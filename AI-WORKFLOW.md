# AI Workflow

This project was built with [Claude Code](https://claude.com/claude-code) (Claude, Anthropic's CLI coding agent) as the primary author, working directly in this repository — not a chat-and-paste workflow. The account below is written from inside that same tool, describing how the work actually happened, not a reconstruction from memory days later.

## Tools

- **Claude Code**, working directly against the repo: reading/writing files, running `dotnet build`/`dotnet test`/`dotnet ef`, starting and driving the API and Angular dev servers, issuing live HTTP requests (`curl`) against the running API, and driving the actual browser (via a Chrome automation extension) to exercise the Angular UI end-to-end.
- **Docker + Testcontainers, Playwright, NetArchTest**: the verification tooling. Every claim of "working" in the later sessions is backed by a real run: integration tests against a real SQL Server 2022 and Azurite container, E2E against a running stack in Chrome, and architecture rules checked against the compiled assemblies.
- **A persistent memory system** (plain files under a project-scoped memory directory, indexed by a `MEMORY.md`), used to carry project-specific facts — architecture decisions, known gaps, workflow preferences — across sessions that don't share conversation context. This mattered concretely: a later session found the written implementation plan not by being told where it was, but by searching the filesystem once memory pointed at "check outside the repo," then wrote back *where* it had found it so the next session wouldn't repeat the search.
- **Subagent delegation.** Early on, once: a research-only agent was sent to read every DI-registration extension method, JWT/Hangfire/Storage config class, and the API project's `.csproj` across four projects, and report back exact method signatures and required config keys — so that `Program.cs` could be wired up correctly in one pass instead of iterative trial and error against build errors. Later, while implementing the testing plan and the requirements review, the frontend work (Karma specs with Material harnesses, the ESLint UI-02 rule, the Playwright suite, and the UI side of contract changes) was delegated to a parallel agent with an explicit written API contract, while the main session worked on the backend. The main session then ran that agent's output itself rather than trusting its report, which is how the E2E selector bug below was caught.

## Workflow structure

Work proceeded layer by layer over several sessions (visible in the commit history: Domain → Application → Persistence → Infrastructure → API → bug fixes → tests → frontend → docs), each session picking up where the last left off. Because sessions don't automatically share context, each one re-established ground truth before making changes, rather than trusting a summary: reading `git log` and `git status` to see what actually exists, reading the actual source of the layer being extended, and — critically — running the code, not just reading it.

A repeated pattern shows up across sessions: **`dotnet build` succeeding was never treated as proof of correctness.** After wiring up `Program.cs`, the API was started for real, `curl`'d through a full scenario (mock login → create claim → open reserve → approve → check audit log), and that live pass is what actually caught two real bugs that a clean build and even passing unit tests would have missed entirely (see below). The same discipline was applied to the frontend: after `ng build` succeeded, the app was driven in an actual browser against the live API, which is how a tab-state bug was found that no amount of reading the component code would have surfaced.

## Representative prompts

These are the actual user prompts (verbatim) from this project, in order, with what they were asking for:

1. **"continue implementing the plan"** — the opening prompt of a session with no other context. It required finding the actual implementation plan (not in the repo — in the user's Downloads folder), reconciling it against `git log`/`git status` to see what was actually done versus stubbed, and picking up the highest-value unfinished piece (wiring the API layer, which existed as disconnected controller files with an un-modified `Program.cs`).
2. **"what left"** — a status check partway through, asking for an honest gap analysis against the plan's own deliverables checklist rather than a summary of what had just been done.
3. **"make frontend"** — a large, open-ended build request (the plan's entire §8, an Angular app from nothing) with no further specification; required inferring scope from the plan document itself rather than re-asking.
4. **"fix that bug"** — a terse follow-up referring to something flagged as *unverified* (not confirmed broken) in the previous turn. Taking the request at face value without re-investigating would have meant "fixing" code that turned out to have no bug — see below.
5. **"do the docs"** — this document and its two companions, after the user was given the specific list of what the plan still required.
6. **"check C:\\…\\DICEUS Claims Module — Testing Plan.docx check if exverything is correctly to the testing plan"** — an audit prompt with a 10-section test plan as context. It started as a comparison (test IDs against actual test methods) and was answered with a gap table rather than code changes.
7. **"fix all the sections"** — the follow-up that turned the audit into implementation. It was structured as backend first (defects, then tests layer by layer in the plan's own priority order), with frontend tests and E2E handed to a parallel agent, then CI, smoke tests and docs.
8. **"make docker run"** and **"fix issues"** — short operational prompts. Both led to real defects being found by *running* things: the Docker stack's persisted data exposed the claim-number format break; "fix issues" was scoped to the open items in the previous answer rather than invented work.
9. **"check C:\\…\\DICEUS_Fullstack_Technical_Assessment (1).docx check if exverything is correctly to the requirements and what else has to be done"** — a requirements audit of the whole deliverable against this brief. It was answered with a mismatch table and one explicit design question (reserve adjust semantics). The user replied with the proposed order of work without choosing an option, so the recommended option was applied and flagged as such.

## Where AI helped most

Layer-by-layer implementation of well-specified, mechanical work — EF Core entity configurations, CQRS command/query handlers following an established pattern, FluentValidation rules, xUnit test suites once the testing approach was settled — went fast and required little correction once a pattern was established for the first instance in a layer. Writing 125 tests across three projects in one session, each following the same fixture patterns, is representative: once the SQLite-vs-InMemory test-provider decision was made (see below), the remaining test classes were mechanical.

AI was also effective at diagnosing failures from concrete evidence — a SQL Server error number, a stack trace, an HTTP response body — and going straight to a root cause rather than guessing. Both production bugs below were found and fixed within one exchange each once a live repro existed.

## Where AI needed correction or extra scrutiny

**Two real production bugs shipped in earlier layers and were only caught by insisting on a live, end-to-end pass instead of trusting the build:**

1. **`ClaimNumberGenerator` composed `.FirstAsync()` onto `Database.SqlQueryRaw<long>("SELECT NEXT VALUE FOR ...")`.** This compiles, and would pass any unit test that mocks the database. Against a real SQL Server, EF Core translates that composition into a `TOP(1)`-wrapped derived table, and SQL Server rejects `NEXT VALUE FOR` inside a derived table outright (error 11719) — so *every* claim creation failed at runtime. Found by running the API for real and hitting `POST /api/claims`; fixed by materializing with `ToListAsync()` and indexing `[0]` instead, which avoids the composition entirely.
2. **`ClaimsDbContext` never marked `BaseEntity.Id` as `ValueGeneratedNever()`.** Every ID is a client-generated GUID, but without that annotation EF Core's default convention assumes it *might* be database-generated — which breaks specifically when a new child entity is added to an *already-loaded* aggregate (e.g. opening a second reserve on an existing claim): EF sees a non-default key on the new row and emits an `UPDATE` instead of an `INSERT`, throwing a concurrency exception against a row that doesn't exist yet. This is invisible when creating a brand-new aggregate with its children all inserted together (the common case exercised first), and only showed up when testing a second, independent write against an existing claim — again, only found by driving a real multi-step scenario against a real database rather than a single happy-path check.

**A frontend bug from the same root cause (trusting compilation over interaction):** the claim-detail page's `mat-tab-group` had no bound `selectedIndex`. `ng build` and a first glance at the rendered page gave no signal anything was wrong. It only surfaced when actually clicking through a multi-step scenario in a real browser — approve a reserve, watch the page silently jump back to the Overview tab — which is exactly the kind of interaction a static review or a component unit test wouldn't exercise.

**A case of correctly *not* fixing something on request:** asked to "fix that bug" referring to the FNOL intake form's dropdown interaction, which had been reported as *unverified* (not confirmed broken) due to browser-automation tool instability in the prior session. Re-investigating properly — rather than assuming the earlier caution meant a real bug existed — required retrying the same interaction under controlled conditions (batched click-then-screenshot calls) until getting a clean signal, which showed the dropdown and form validation both worked correctly. The actual problem was the automation tool intermittently failing (and, worse, one of its actions silently no-op'ing while still reporting success — caught by cross-checking a supposedly-already-set field's "previous value" on a later call). No code was changed, because no code was broken; the honest outcome was reporting that explicitly rather than making a speculative "fix" to quiet the request.

**A self-caught bad test assumption, not a production bug:** while writing `OpenReserveCommandHandlerTests`, the first version of a test asserted that submitting a single reserve above the Manager authority tier would trip the BR-R-07 $10M aggregate cap. It doesn't — a `PendingApproval` reserve contributes nothing to `CurrentAmount` until decided, so a single large submission can never itself exceed the cap. This is a real, documented gap in the business rule (see `ARCHITECTURE.md` §5), but the first instinct was to write a test asserting the *intended* behavior rather than the *actual* one; the test was corrected to assert what the code actually does, and the gap was written up rather than silently patched, since closing it is a product decision (re-check the cap on approval? include pending amounts in the sum?) that wasn't asked for. (It was closed later, when the user asked for the open issues to be fixed: approval now re-checks the cap and requires an explicit Manager override.)

### Later sessions: errors caught while implementing the testing plan and the requirements review

These are the most instructive corrections, because several are the AI's *own earlier output* being wrong:

1. **An AI-written fix introduced two production regressions.** An earlier session added tenant isolation, a global query filter on `OrganizationEntityId`. It was verified by hand with a quick query and looked correct. When integration tests finally ran against real SQL Server, they showed two things the fix had broken:
   - `ReserveHistory` rows had always been created without an organization, so the new filter hid every reserve change from everyone. Approving failed with "history does not belong to component", adjusting threw a duplicate-key 500, and balances read 0.
   - Hangfire jobs run with no HTTP user, so the filter resolved to `Guid.Empty` and GL posting and SLA monitoring silently processed nothing.

   The unit tests couldn't see either problem: their hand-rolled test `DbContext` has no tenant filter. The fix was to stamp the tenant at creation, let jobs read past the filter explicitly, add a backfill migration, and add a `SaveChanges` guard that makes an empty tenant fail loudly next time.
2. **An AI-written test harness had never worked, and was quietly damaging.** The integration project's `WebApplicationFactory` overrode the connection string with `ConfigureAppConfiguration`. That applies too late for `Program.cs`, which reads the connection string eagerly, so the tests migrated the *developer's LocalDB* and then failed against an empty container. It went unnoticed at first because Docker wasn't running, so every test "failed for an environmental reason". The fix is `UseSetting`, and the lesson is to check what an unrunnable test would do, not just that it compiles.
3. **An AI audit claim was wrong.** A prior gap analysis stated that all five architecture rules held "when checked by hand". The first real NetArchTest run showed Domain referenced MediatR (`DomainEvent : INotification`), violating A-01. The fix moved domain events to plain records, wrapped in `DomainEventNotification<T>` in the Application layer.
4. **A structural change broke existing data.** An earlier session changed claim numbers from 6 to 7 digits and updated the validation regex. Every test passed, because tests create fresh data. Running the Docker stack against its *persisted* volume turned the whole claims list into a 500. The fix accepts legacy 6-digit numbers on load (a business identifier is never rewritten) while new numbers stay 7-digit.
5. **A subagent's E2E selector didn't match the real DOM.** The delegated agent wrote Playwright tests that located the active FNOL step by `aria-expanded="true"`, which Material 18's horizontal stepper never sets. It reported the suite as "type-checks, not executed". Running it against a live stack showed the failure; the fix was to select the one visible panel.
6. **Seeded data contradicted the specification, and the tests encoded the contradiction.** The 49-pair transition test asserted "whatever is seeded". The seed allowed Draft → Closed, which BR-C-06 forbids, and granted every transition to every role, which made WF-05's 403 impossible. The test was changed to assert a *documented* graph, and a second test now checks the real seeded table against it.
7. **A requirements review found semantics that no test could catch.** Reserve adjustment took a *delta*, while the brief's ReserveHistory fields (PreviousAmount/NewAmount/ChangeReason) and BR-R-01 ("amount > 0") imply a new total. This was raised with the user as a decision. With no answer, the recommended option was applied and called out: new-total with a required reason, plus a backfill migration for existing history.

### Hands-on UI review: errors caught by using the app as a claims handler

Clicking through the app as a handler surfaced problems that the passing test suites had missed:

1. **The AI answered "the API works" when the real fault was in the form.** Asked why Policy Number and Client Name were never saved, the first check showed the API storing and returning the policy correctly. The API log showed the real cause: the user had typed policy numbers that matched nothing, and the form silently dropped the text. Separately, the AI-written autocomplete had no option `[value]`, so Material blanked the search box straight after a pick. Reverting the fix made the new test fail (`Expected '' to be 'POL-2026-000001 — Acme Corp'`), which confirmed the bug. The fix made the form require a picked policy or "Unknown policy", and made empty searches say "No matching policies".
2. **The UI offered actions the API would always refuse.** Approve showed on the user's own request (the API returns 403 under the four-eyes rule), and Adjust showed on reserves with a pending change (the API returns 422). The tests had only checked role gating, not these rules, so both looked like broken features.
3. **A security gap in AI-written handlers.** Open and Adjust honoured the $10M-cap override flag from **any** role; only Approve checked for Manager. A Handler could bypass BR-R-07 by sending the flag directly. It was found while wiring the UI's override dialog, and fixed with tests for both handlers.
4. **An unbounded input reached the database.** A reserve of `1e20` overflowed `DECIMAL(19,4)` and returned a generic 500. There is now a validated maximum on both sides, plus length limits on every text field to match its column.
5. **A requirements re-check found a missed requirement.** The brief says `GET /api/policies/{id}/coverage` is "used during FNOL to display available coverage types". The endpoint and its service method existed, but no screen called them. FNOL now shows the picked policy's coverages.

## AI-generated vs. directed and refined

- **Written by the AI (Claude Code):** effectively all code, tests, migrations, infrastructure (Bicep, CI) and first drafts of every document in this repository.
- **Supplied and decided by the candidate:**
  - the requirements: the assessment brief, the FRS/DDL and the testing plan;
  - the order and scope of work, through the prompts above;
  - which proposed options to accept: for example, fixing the code to match the testing plan rather than the reverse, and the order used to close the requirements gaps.
- **How output was validated:** by running it. Builds, then unit tests, then integration tests against real SQL Server and Azurite, then the Docker stack, then Playwright E2E in a real browser. Several findings above only appeared at the later stages.

## What this means for reviewing this codebase

Treat a clean `dotnet build`/`ng build` and passing unit tests as necessary, not sufficient. Both real production bugs in this codebase were invisible to both and only surfaced under an actual live, multi-step scenario. If extending this module, the same discipline applies: run it, don't just compile it.
